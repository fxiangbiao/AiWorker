# 全栈产品开发工作流

五阶段开发方法论。每阶段完成后暂停，等待确认再进入下一阶段。

## 阶段 1：需求分析

- 用 `web_search` / `web_fetch` 调研竞品、技术趋势、最佳实践
- 用 `fs_list` / `fs_read` 梳理现有代码库相关模块、接口、依赖链
- 明确功能边界、约束条件、优先级（P0 阻塞 / P1 核心 / P2 锦上添花）
- 评估跨平台影响
- 复杂需求用 `/debate` 多专家交叉验证

## 阶段 2：方案设计

生成 Sprint 计划文档到 `plans/sprint-NN-<slug>.md`，必须包含：

1. **目标摘要**：1-2 句话
2. **任务拆分**：每个任务标注优先级 + 预估改动文件
3. **文件变更清单**：新建 vs 修改，明确路径
4. **依赖关系图**：（如有 3+ 任务）ASCII 图
5. **验证标准**：每个任务验收条件（编译/类型检查/lint/测试/手动验证）
6. **风险与对策**：高风险点 + 降级方案

## 阶段 3：编码实现

### 3.1 实现前 — 设计自查

- **数据流**：状态所有者是谁？传递路径是什么？有无并发写风险？
- **错误路径**：每个分支的异常如何传播？降级策略？超时/重试策略？
- **边界条件**：空/极大/极小/负数/null/undefined/NaN 输入是否处理？
- **跨平台**：路径、编码、进程管理、换行符在各平台上是否一致？
- **输入信任边界**：所有外部输入（用户/LLM/API/DB/文件）是否校验？注入风险是否消除？
- **资源生命周期**：事件监听器、定时器、文件句柄、子进程的创建和销毁是否一一对应？退出路径是否完整？
- **向后兼容**：接口签名/配置格式/DB schema 变更是否破坏现有调用方？

### 3.2 编码规范

通用原则（与语言无关）：
- 遵循项目现有风格，用 `fs_read` 参考同类文件后再写
- 复用已有工具和库，不重造轮子
- 类型/接口定义集中管理
- 不添加注释，除非绝对必要说明复杂逻辑
- 依赖注入优于全局变量，不可变优于可变，显式优于隐式

语言适配要点：
- **JS/TS**：ESM `.js` 扩展名、kebab-case 文件名
- **Python**：type hints、context manager、dataclass
- **Go**：显式 error 返回、defer 清理、interface 隔离
- **Rust**：Result/Option、borrow checker、derive 宏
- **其他**：先查项目已有模式再套用

### 3.3 实现后 — 自审查

用以下通用思维模型全面审查（非穷举 bug 清单，而是发现任意问题的方法）：

**A. 不变量检验**
每个模块/函数有不变量假设（"X 一定不为空""Y 一定在 0-100 之间"）。逐个确认这些假设在所有代码路径上是否成立。

**B. 失败模式推演**
对每个关键组件自问：如果它失败了，上游感知到吗？下游会收到什么？整个链路如何降级？不会静默吞错或无限重试。

**C. 状态空间扫描**
系统有哪些状态？哪些状态转换是合法的？非法状态是否能被触发（如并发交错、异常中断）？是否存在无保护的过渡状态？

**D. 资源生命周期追踪**
每个资源（连接/句柄/监听器/定时器/锁/子进程）从创建到销毁的路径是否完整？异常退出路径是否有 finally/cleanup？

**E. 数据流端到端追踪**
从数据进入系统到最终消费，每一步检查：格式是否变化（snake_case↔camelCase、序列化/反序列化）、顺序是否保持、是否可能丢失或重复。

**F. 接口边界审查**
跨进程/跨线程/跨网络/跨语言的边界处是最容易出错的区域。检查：编码一致性、超时处理、部分失败、幂等性、向后兼容。

**G. 时序分析**
异步/并发/事件驱动场景下：事件顺序有保证吗？竞态窗口多大？回调/监听器注册时机是否可能错过事件？Close/shutdown 的同步性。

**H. 输入面盘点**
列出所有外部输入源（用户输入、API 响应、文件内容、环境变量、命令行参数）。每个源是否校验了：类型、范围、格式、编码、大小、恶意内容？

## 阶段 4：测试验证

三层验证全部通过才算完成。

### 4.1 功能测试
运行项目测试框架（vitest / pytest / go test / cargo test），确保全绿。

### 4.2 类型与代码质量
```bash
npx tsc --noEmit        # TypeScript 类型检查
npx eslint src/         # JavaScript/TypeScript lint
# Python: ruff check + mypy
# Go: go vet + golangci-lint
# Rust: cargo clippy + cargo fmt --check
```

### 4.3 性能与健壮性（复杂功能适用）
- 端到端耗时是否合理
- 长时间运行是否有资源泄漏
- 异常输入下降级行为是否正确
- token / 内存 / 磁盘占用是否可控

## 阶段 5：文档交付

### 5.1 Sprint 计划更新
在计划文档末尾追加执行记录：`| 日期 | 任务 | 提交 |`

### 5.2 README.md 更新
（重大功能变更时）新增功能说明、命令/参数、环境要求。

### 5.3 AGENTS.md 更新
（架构变更时）核心模块说明、新增文件说明、配置项变更、编码规范补充。

### 5.4 代码提交
```bash
git add -A
git status
git commit -m "<type>: <描述> — <要点>"
git push
```
- type: feat / fix / refactor / docs / test / chore
- 示例：`feat: Sprint 15 Markdown 视觉优化 — 语法高亮 + 表格美化 + 链接渲染`
