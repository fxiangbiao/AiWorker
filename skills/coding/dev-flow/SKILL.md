# 全栈产品开发工作流

五阶段开发方法论。每阶段末尾使用 question 工具询问用户：进入下一阶段、还是修改当前阶段。

## 快速判断：走哪条路径？

**功能开发 / 架构变更**（涉及 3+ 文件、新模块、未知技术栈）→ 五阶段流程

**缺陷排查 / 行为异常** → 轻量排查路径（见下）

**单文件 bug 修复、样式微调、文案修改** → 简化流程（跳过 Phase 1-2，直接从 Phase 3 开始）

### 轻量排查路径（缺陷 / 行为异常时）

1. 复现取证：拿到完整错误、日志、截图，明确「预期 vs 实际」
2. 列出 ≥2 个候选根因，逐个用最小脚本/单测验证，排除而非猜测
3. 三分定位：设计行为（与规范一致）/ 代码缺陷 / 环境或模型限制，结论需证据支持
4. 修复后补可复现该 bug 的回归测试（先见 fail 再改到 pass）；扫描同类路径（同一函数的其他调用方、类似实现）确认无同类隐患
5. 结论为「设计行为」时，给出「保持现状 or 增强」建议由用户决策

## 阶段 1：需求分析

- 用 `web_search` / `web_fetch` 调研竞品、技术趋势、最佳实践
- 用 `fs_list` / `fs_read` 梳理现有代码库相关模块、接口、依赖链
- 明确功能边界、约束条件、优先级（P0 阻塞 / P1 核心 / P2 锦上添花）
- 评估跨平台影响
- 复杂需求用多专家交叉验证

## 阶段 2：方案设计

生成 Sprint 计划文档到 `plans/sprint-NN-<slug>.md`，必须包含：

1. **目标摘要**：1-2 句话
2. **任务拆分**：每个任务标注优先级 + 预估改动文件
3. **文件变更清单**：新建 vs 修改，明确路径
4. **依赖关系图**：（如有 3+ 任务）ASCII 图
5. **验证标准**：每个任务验收条件（编译/类型检查/lint/测试/手动验证）
6. **风险与对策**：高风险点 + 降级方案

### 🔲 阶段门控
使用 question 工具询问："方案设计完成。进入编码实现 / 修改方案？"

## 阶段 3：编码实现

### 3.1 实现前 — 设计自查

- **数据流**：状态所有者是谁？传递路径是什么？有无并发写风险？
- **错误路径**：每个分支的异常如何传播？降级策略？超时/重试策略？
- **边界条件**：空/极大/极小/负数/null/undefined/NaN 输入是否处理？
- **跨平台**：路径、编码、进程管理、换行符在各平台上是否一致？
- **输入信任边界**：所有外部输入（用户/LLM/API/DB/文件）是否校验？注入风险是否消除？
- **资源生命周期**：事件监听器、定时器、文件句柄、子进程的创建和销毁是否一一对应？退出路径是否完整？
- **向后兼容**：接口签名/配置格式/DB schema 变更是否破坏现有调用方？

### 3.2 编码规范

通用原则（与语言无关）：
- 遵循项目现有风格，用 `fs_read` 参考同类文件后再写
- 复用已有工具和库，不重造轮子
- 类型/接口定义集中管理
- 不添加注释，除非绝对必要说明复杂逻辑
- 依赖注入优于全局变量，不可变优于可变，显式优于隐式

语言适配要点：
- **JS/TS**：ESM `.js` 扩展名、kebab-case 文件名
- **Python**：type hints、context manager、dataclass
- **Go**：显式 error 返回、defer 清理、interface 隔离
- **Rust**：Result/Option、borrow checker、derive 宏
- **其他**：先查项目已有模式再套用

### 3.3 实现后 — 自审查

用以下通用思维模型全面审查（发现任意问题的方法，非穷举清单）：

**A. 不变量检验**：每个模块/函数的假设在所有代码路径上是否成立

**B. 失败模式推演**：关键组件失败时上游是否感知、下游收到什么、如何降级

**C. 状态空间扫描**：系统有哪些状态、哪些转换合法、非法状态是否可达

**D. 资源生命周期追踪**：每个资源（连接/句柄/监听器/定时器/锁/子进程）的创建→销毁路径完整性

**E. 数据流端到端追踪**：从进入系统到最终消费，格式/顺序/丢失/重复检查

**F. 接口边界审查**：跨进程/跨线程/跨网络/跨语言的边界处（编码/超时/部分失败/幂等性/兼容性）

**G. 时序分析**：异步/并发/事件驱动下的事件顺序、竞态窗口、回调注册时机

**H. 输入面盘点**：所有外部输入源的类型/范围/格式/编码/大小/恶意内容校验

## Code Review（阶段 3 → 4 之间）

实现完成后、测试验证前，执行独立代码审查：

- 使用 git diff 获取全部改动
- 逐文件检查，按 P0（崩溃/安全）→ P1（功能断裂）→ P2（代码质量）三级标注
- 发现 P0/P1 问题立即修复并重新审查，P2 按优先级修复
- 输出问题汇总表：级别 / 文件 / 问题描述 / 修复方案

使用 question 工具询问："审查完成，已修复 X 个问题。进入测试验证 / 继续审查？"

## 阶段 4：测试验证

三层验证全部通过才算完成。

### 4.1 功能测试
运行项目测试框架（vitest / pytest / go test / cargo test），确保全绿。修复型改动必须新增能复现该 bug 的回归测试（先见 fail，再改到 pass）。

### 4.2 类型与代码质量
```bash
npx tsc --noEmit        # TypeScript 类型检查
npx eslint src/         # JavaScript/TypeScript lint
# Python: ruff check + mypy
# Go: go vet + golangci-lint
# Rust: cargo clippy + cargo fmt --check
```

### 4.3 构建验证（Web 项目适用）
```bash
npm run web:build 或 cd web && npx vite build
```

### 测试失败处理
任何一项不通过 → 输出失败详情 → 回到阶段 3 修复 → 重新走 3.3 自审查 → 重新测试。

### 修复后影响面复查
改动函数的所有调用方与同类实现都要扫描，确认无同类隐患（如改 fs_write 路径解析 → 检查 terminal_exec/MCP 等写入通道）。UI 类修复提交前请用户确认实际效果。

## 阶段 5：文档交付

### 5.1 Sprint 计划更新
在计划文档末尾追加执行记录：`| 日期 | 任务 | 说明 |`

### 5.2 README.md 更新（按需，非每次必做）
- 用途：给**人类**阅读——快速了解、上手使用项目的指引
- 仅在用户可见行为变化时更新（新增功能、命令/参数、环境要求）
- 判断标准：本次改动是否让读者认知与实际不符？相符则无需更新

### 5.3 AGENTS.md 更新（按需，非每次必做）
- 用途：给 **AI** 阅读——快速掌握架构设计、项目规范/约束，避免产出偏差
- 仅在架构/模块/规范/配置约定变化时更新（核心模块说明、新增文件、配置变更、编码规范补充）
- 判断标准：本次改动是否让 AI 对项目的理解与实际不符？相符则无需更新

### 5.4 代码提交
```bash
git add -A
git status
```

生成 commit message（格式：`<type>: <描述> — <要点>`），**等待用户审核通过后由用户手动执行** `git commit` 和 `git push`。

- type: feat / fix / refactor / docs / test / chore
